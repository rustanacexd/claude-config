## Lessons from past sessions

Approved by the owner after a `pstack:reflect` review. These add to the pstack skills, which update from upstream.

- **Porting a reference design.** When a requirement changes one parameter of a design you copy, such as a whole screen becoming one window, keep the reference's mechanism and change only that parameter. Swapping in a different API is a design decision. Tell the person before you make it.
- **Subagents that write files** get their own worktree from the start. Never let a subagent share your checkout. In a repo Orca manages (`orca worktree list --repo path:<checkout>` succeeds), create it with `orca worktree create --repo path:<checkout> --name <name> --setup run --json`, pass the subagent `result.worktree.path`, and remove it with `orca worktree rm --worktree path:<path> --run-hooks`. Only in a repo Orca doesn't manage, use `isolation: "worktree"` or `git worktree add`. They skip the repo's `orca.yaml` setup and archive scripts.
- **"Merge when green", "merge the PRs when ready".** Run poteto-mode's Babysit playbook, then its Shipping playbook. Don't hand-build polling loops.
- **Measure runs, ablations, before/after numbers, CPU or memory tables.** Open the `pstack:benchmark-checklist` SKILL.md before you report or act on the numbers.
- **Stubbed or moved stages.** If the after-run stubs, skips or moves a stage the before-run did, report the change as work moved, not cost cut, and name what is no longer measured.
- **Prove the cause before asking.** Before offering the person a choice that depends on what causes a problem, confirm the cause with an ablation on the same runner, changing one input.
- **Live-desktop checks never gate.** Only checks fed controlled synthetic input may fail a build. Checks that read focus, real windows or the GPU only report. Never fix a flaky live check with a longer timeout or a retry.
- **Before spawning merge verifiers.** Read the base branch's classic protection (`gh api repos/<o>/<r>/branches/<base>/protection`), not only rulesets. If it requires conversation resolution, confirm zero unresolved `reviewThreads` on every PR in the set first, and read them again after every push, because review bots open new threads on each push. A thread fix changes the patch and voids any verdict taken before it.
- **Self-scheduled wakeups.** Write the prompt as a check of recorded state ("read <artifact>; if the step is already recorded, continue from there"), never as a list of orders. Cancel or replace the pending wakeup when the step it serves completes.
- **A gate redefined after it failed.** If a check that guards an irreversible action fails, and you narrow or replace the check, that is a new decision. Stop and send the action back to the person with the failure stated. Do not run the irreversible step on the narrowed check.
- **Before you call something impossible.** If a sibling system already does it, such as another repo whose CI builds with the same credentials, read how it does it first. Only then tell the person it can't be done or that they must rebuild something.
- **Away operator: approve, don't perform.** Ask the away person for permission to act, then do the action yourself. Hand them a step only when the tooling blocks you, and then as one tap or one line. Treat their "done" as a claim. Check the real system (for example `gh secret list` timestamps) before you build on it.
- **Commands a person will paste.** Give one line, with absolute paths and no `<placeholders>`. Check it for the shell it will run in (zsh, Claude's `!` mode, a phone). A `!` paste runs every line on the host. If it can't be one line, save it as a script and give one short call.
- **Long jobs say where they run.** When you start or report a job longer than a few minutes, say in the same sentence where it runs (host, VM, CI, cloud API) and what it touches.
- **`/correct` evidence includes agent transcripts.** In "Find the mistake classes", also read the main and subagent transcripts (`~/.claude/projects/<slug>/<session>.jsonl` and `<session>/subagents/*.jsonl`). Tally classifier denials, hook blocks and tool errors by kind. Keep the tally script in the repo or skill, not `/tmp`.
- **A bug that stops reproducing with no named mechanism stays open.** Green runs after an unrelated change mean the race moved, not that it was fixed. Report it as "cause unknown" and keep the issue open until a mechanism is shown.
- **Open the playbook the request names.** When a request names a poteto-mode playbook ("hill climb", "babysit", "bug fix"), open that playbook even when the request arrives wrapped in another skill such as `/sharpen`. Copy its steps, stop rule and decision log in.
- **A new check proves both directions before it gates.** Run it locally, and show it fails on a known-bad artifact and passes on a known-good one, before it can fail a slow pipeline such as a release or a measure run. A checker bug costs a whole cycle.
- **Waiting on the Codex PR review.** When a PR opens or gets a push, start an independent reviewer on another model at the same time as Codex, not after Codex stalls, on every PR including docs-only ones. Wait for Codex only with `~/.claude/scripts/codex-review-wait.sh <owner/repo> <pr>` in the background (cap 10 minutes; exit 0 done, exit 3 stalled), never a hand-written polling loop. On exit 3, go with the other reviewer's verdict. Start the next task while reviews run.
